Microsoft's current guidance requires consent transmission for EEA, UK and Swiss traffic through supported mechanisms. [Microsoft consent requirements](https://about.ads.microsoft.com/en/blog/post/march-2025/providing-user-consent-signals-on-your-microsoft-campaigns-by-may-5-2025).

For standard UET, `ad_storage` is `granted` or `denied`; Tag Helper exposes the event consent state as `asc`. Before permission, no events is valid Basic Consent Mode; Advanced mode instead runs with denied consent. Subsequent permitted events should show granted. Microsoft also supports automatic consent discovery from standard mechanisms unless disabled, so a wrapper need not contain those strings. Receiver verification is per event: **Test your tag → Consent Status: Present/Not present**. The dashboard's Healthy label means greater than 75% coverage over seven days, not perfect current-session coverage. The cited documentation describes helper states; it does not establish a raw uppercase G/D encoding for the proprietary Shopify stream. [MicrosoftDocs: implementation and validation](https://github.com/MicrosoftDocs/Advertising/blob/main/advertising/msa-help/hlp_BA_CONC_UET_Consent.md).

Shopify loads app pixels only when all declared required permissions are allowed. Pixels can separately read `init.customerPrivacy` and subscribe to `visitorConsentCollected`. Thus, strict gating establishes an admission condition, not evidence that Microsoft received a valid consent signal. The deployed app's proprietary transport requires its own receiver check; a top-frame UET queue update cannot be assumed to affect it. [Shopify Pixel Privacy](https://shopify.dev/docs/api/web-pixels-api/pixel-privacy).

**Smallest remediation, only if the trace establishes a gap:** preserve the existing app's purpose requirements and Basic gating. For a faulty standard storefront stream, connect the existing tag to Shopify's initial effective permissions and consent-change event, queueing the supported `consent` default/update commands with `ad_storage` before dependent events and on revocation/navigation. Grant only when the tag's required permissions allow it; avoid adding another event-producing tag. This is a conditional design, not an executed or runtime-tested patch. Shopify's `Allowed` methods incorporate region, merchant settings and user choice; do not infer permission from blank consent strings or manually change privacy cookies. [Shopify Customer Privacy API](https://shopify.dev/docs/api/customer-privacy).

If only `shop-wpa` fails the receiver check, prepare the exact trace for a supported Microsoft app repair. Do not guess query parameters or rewrite the vendor worker. If automatic consent and both streams pass, no additional bridge is justified.

Required tests:

- Record actual privacy `getRegion()`, effective permissions, tag ID, request initiator and consent state; a Spain market/language selection is not proof of EEA geolocation.
- In isolated sessions test unchosen, decline, grant, marketing-only revocation and reload/navigation, separating storefront and app requests. Advanced-denied verification also inspects advertising identifiers; an HTTP response alone proves neither consent nor conversion acceptance. [Microsoft advanced-mode verification](https://about.ads.microsoft.com/en/blog/post/february-2026/advanced-consent-mode-preserving-accurate-measurement-while-respecting-user-privacy).
- When authenticated access is available, verify receiver consent separately for Page Load and Custom Events, then consented purchase/value/currency/order deduplication through an authorized purchase test. This assessment establishes none of those outcomes.
